# C4 model

## Levels

| Diagram | Scope | Shows | Draw |
|---|---|---|---|
| System context | One software system | The system and the people and external systems connected to it | Always |
| Container | One software system | The containers inside it and what connects to them | Always |
| Component | One container | The components inside it and what connects to them | Only when it adds value |
| Code | One component | Classes, interfaces, functions, or tables | Optional, generate with tooling |

A container is a runtime boundary around code that runs or data that is stored. Examples are a web application, a single-page app, a mobile app, a serverless function, and a database. It is unrelated to Docker containers.

Supplementary diagrams are the system landscape across an organization and the dynamic diagram for one runtime scenario.
The deployment diagram covers one environment.
Clustering, load balancers, replication, and failover go on the deployment diagram.
Draw a deployment diagram per environment when clustering or failover matters.

## Placement

- Draw what the code and deployment files show, and mark planned parts as planned.
- Add a component diagram only when it adds value.
- A diagram for one decision goes under that ADR's More Information.
- Whole-system diagrams go in the architecture docs folder, or `docs/architecture/`.
- If the project uses arc42, link its section 9 to the ADR files.

## Notation rules

- Every diagram has a title naming its type and scope.
- Add a key for shapes and colours when the tool draws none.
- Every element has a type and a short description. Every container and component also has a technology.
- Every line is one relationship in one direction. Its label is specific and matches the direction, so avoid a bare "Uses".
- Lines between containers carry the protocol, such as `JSON/HTTPS` or `AMQP`.

## Mermaid C4

GitHub renders `mermaid` code blocks in Markdown files. The Mermaid documentation marks C4 as experimental, so use only the elements below and check that the diagram renders.

- Mermaid C4 draws no legend, so write a one-line key under every diagram.
- Shapes are placed in statement order. Reorder statements when lines cross or labels overlap.
- Use `Rel` for every line, because `BiRel` draws the two-way line the notation rules discourage.

| Element | Parameters |
|---|---|
| Diagram types | `C4Context`, `C4Container`, `C4Component`, `C4Dynamic`, `C4Deployment` |
| `title` | Free text on one line after the diagram type |
| `Person`, `Person_Ext` | `alias, label, ?descr` |
| `System`, `System_Ext`, `SystemDb`, `SystemQueue` | `alias, label, ?descr` |
| `Container`, `Container_Ext`, `ContainerDb`, `ContainerQueue` | `alias, label, ?techn, ?descr` |
| `System_Boundary`, `Container_Boundary` | `alias, label`, followed by a block in braces |
| `Rel` | `from, to, label, ?techn` |

## Structurizr DSL

Use it for a long-lived model with several views. It describes the model once and derives each view.

Element syntax is `person <name> [description] [tags]`, `softwareSystem <name> [description] [tags]`, and `container <name> [description] [technology] [tags]`. A relationship is `<identifier> -> <identifier> [description] [technology] [tags]`. A view is `systemContext <system>` or `container <system>` with `include *` and an optional `autoLayout` of `tb`, `bt`, `lr`, or `rl`.

```
workspace {

    model {
        customer = person "Customer" "Buys products online"
        payments = softwareSystem "Payment provider" "Charges cards and issues refunds"
        shop = softwareSystem "Shop" "Lets customers browse products and place orders" {
            webapp = container "Web application" "Serves the storefront and the order API" "TypeScript, Node.js"
            database = container "Database" "Stores products, customers, and orders" "PostgreSQL"
        }

        customer -> webapp "Places orders using" "HTTPS"
        webapp -> database "Reads from and writes to" "SQL"
        webapp -> payments "Charges payments through" "JSON/HTTPS"
    }

    views {
        systemContext shop {
            include *
            autoLayout lr
        }

        container shop {
            include *
            autoLayout lr
        }
    }

}
```
