# Focused assurance

## Model the operation being changed

When a change introduces or alters a trust crossing, identify the actor, protected asset, operation, attacker-controlled values, and enforcement point, and follow the data through the actual callers before choosing controls, because a control chosen from a function name alone often sits on a path the attacker never uses. An asset can be confidentiality, an account balance, signing authority, an export, or available compute, and a trust boundary is where authority or interpretation changes, not every function call. Check one realistic prohibited effect and one valid operation against the model.

<example>
A licensed font download in an online store has the buyer as actor, the font file as asset, and `?file=` as the attacker-controlled value, so the enforcement point is the `/downloads` handler, where `licenses.expires_at` is compared with the current time.
</example>

When an operation spans browser, API, queue, worker, storage, and download hops, as a tenant export does, carry the verified authority through the job and reauthorize retrieval, because a service account's database access does not mean the requesting user has access. The assets include rows, generated bytes, object identifiers, and download grants, and a tenant parameter, job identifier, or stored filter can be attacker-controlled. Check that tenant A cannot request, poll, or download tenant B's export, and that explicitly authorized cross-tenant support operations keep working.

<example>
`POST /exports` stores `tenant_id` from the session in `export_jobs`, and `GET /exports/42/download` reloads the job and compares its `tenant_id` with the caller's before streaming the CSV, so shop A asking for shop B's job 42 gets a 404.
</example>

When an existing service becomes multi-tenant, externally reachable, or agent-accessible, revisit the assumptions it inherited from its former environment and keep the smallest control that enforces the current invariant, because an internal network location, an obscure identifier, and a hidden interface are not authority, and safety in a narrower environment is not evidence for the new boundary. Check the operation through the newly exposed route, including direct calls to the final step.

<example>
An `/internal/rebuild-index` endpoint on a Rails service that relied on the office network gets a signed-in admin check, and a test calls it directly from outside the VPN without going through the admin dashboard.
</example>

## Distinguish a fix from an audit

When asked to implement a feature or repair a defect, examine its reachable boundary and callers, reproduce the known failure before editing where tests exist, add the denied case and an allowed case, and run the relevant existing checks, because that shows the fix covers the reported path without breaking legitimate use. Keep the work to that path and the code that shares its root cause, and report other confirmed variants as follow-ups, because unrelated infrastructure, scanner installation, or a repository-wide audit changes the task the user asked for. Check that the negative case fails for the missing control before the fix, not for a broken fixture or an unavailable service.

<example>
For a report that `GET /api/orders/17/receipt` shows receipts to anonymous callers, the test first gets a 200 on a receipt, then the fix adds the missing owner check, and a second test keeps the customer able to read their own receipt.
</example>

When a complete security audit is requested, establish the authorized code, services, environments, credentials, and permitted test effects first, select applicable requirements from a named stable standard version, and examine trust crossings and abuse cases, because marking every threat name as reviewed gives false assurance. A local code review does not authorize live exploitation or prove deployed controls, and missing coverage stays unknown and does not count as a passing control. Check each candidate finding for its attacker prerequisite, reachable sink, failed invariant, and concrete impact before assigning severity.

<example>
An audit of the `admin/` folder reports `admin/export.ts` as a finding only after showing that an unauthenticated visitor reaches it and receives the `SELECT * FROM users` result, and it lists the unreviewed `workers/` folder as not covered.
</example>

When reviewing a security-sensitive diff, inspect removed controls and affected callers, use history where it explains their purpose, and once a root cause is confirmed, search related implementations and verify each match, because similar syntax alone is not a vulnerability. Write the search so that it first matches the known defect and then excludes a nearby safe implementation before generalizing it. Check each hit by reading its caller and its sink.

<example>
A diff that deletes the `canEdit(user, booking)` guard that throws `ForbiddenException` is traced to the callers that relied on it, and after the gap is confirmed in `BookingController.update`, a search for `bookingService.save(` without `canEdit` finds `BulkBookingController` and skips the read-only `PublicCalendarController`.
</example>

## Verify misuse resistance and native boundaries

When designing a security API or configuration, offer semantic operations with safe defaults instead of caller-selected primitives and bypass flags, because every option a caller can choose is one some caller will eventually choose wrongly. A documented dangerous option is still dangerous, but compatibility constraints may call for an explicit migration and not an abrupt break. Check missing, null, empty, zero, negative, and incompatible settings, and confirm that omitted or invalid configuration cannot disable verification or substitute default credentials.

<example>
A Python `fetch_json(url)` helper reads `verify_tls` from config and treats `""`, `None`, and `0` as "verify", and the test confirms the certificate is still checked for each of those values.
</example>

When changing C, C++, FFI, or a native parser, verify buffer bounds before pointer formation, track ownership across error paths, check size arithmetic before allocation, update state only after allocation succeeds, and handle zero-size allocation as the target standard defines, because a memory-safe caller does not make a native dependency memory-safe. Exercise truncated data, zero and oversized lengths, allocation failure, and freed-object paths with the sanitizers or fuzzing available for the actual toolchain, and test both instrumented and production builds, since sanitizers find defects but do not prove their absence or justify a language rewrite.

<example>
A native image-resize addon called from Node checks `len <= UINT32_MAX - header_size` before allocating `len + header_size`, and its test feeds `len = 0`, `len = UINT32_MAX`, and a truncated buffer under AddressSanitizer.
</example>
