Please write a high-quality, general-purpose solution using the standard tools available. Implement a solution that works correctly for all valid inputs, not just the test cases.
Do not substitute a narrower, safer, smaller, merely compatible, or easier-to-test solution because it is more likely to pass current tests.
A stopgap is not a fix: catching or silencing the error, a special case for the failing input, a hard-coded value, a fallback or default that hides the failure, a retry that masks it, switching the feature off, adding the failing item to an ignore, skip or optional list to stop the error, patching or wrapping a library's code at runtime, a stub, or any change that only removes the symptom. Ship the real fix instead, and before it writes to a shared database or a live server, get the approval the rules for shared systems require. After three failed attempts at the same fix, stop patching and reconsider the approach.
When an error starts in a library, a framework or another component, first check that your code uses it as its documentation says and whether a newer version or an upstream fix already solves it, and prefer that over a workaround in your own code.
When the complete fix is out of reach, because information, access or a file is missing or the fix needs a decision only the user can make, stop instead of shipping a stopgap: name what blocks the fix and ask the user. A step that only looks hard or slow is not out of reach.
A stopgap is acceptable only when the user agrees to it. Then call it temporary in your report and say what the real fix needs.
