# Running commands

Run one short command for one purpose. Chain commands with `&&` only when each step depends on the step before it, and send independent commands as separate calls in the same turn, so that each one reports its own exit status. A check that may find nothing, such as `grep` or `ls`, ends with a failure status that is not a failure, so do not put it last in a chain.

Use the file tools for files. Read, search, create and change files with the dedicated tools, not with `cat`, `head`, `grep`, `sed`, a heredoc or a patch script in the shell, also in the middle of a longer command. Find a file with the search tool before you name it in a command, and do not guess its name. When a command needs a script, or would need nested quoting, such as code passed through `ssh` or to another interpreter, write the script to a file in the scratchpad with the file tool and run that file.

Leave the timeout at its default. Set it only when you have a reason to expect a longer run, and then to the expected duration with a small margin, never to the maximum out of habit. Start a command that runs for minutes, such as a long build, a full test suite or a server, in the background and continue with other work, because the harness reports when it ends. Do not use `sleep` to wait and do not poll in a loop. Wait for the completion notice, or use the waiting tool that the environment provides.

Build each command from facts. Take paths, flags and tool names from what you read in this session, from the tool's own help output or from its documentation, not from memory. Write the syntax of the shell that the tool runs. Prefer flags that keep a command non-interactive and its output short. When a command fails, read the error and fix the cause or change the command before you run anything again. Rerun a command unchanged only when the error shows a temporary fault, and do not raise the timeout or add a wait in the hope that it helps.
